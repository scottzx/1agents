## 0. 冲突裁决（定稿 · 2026-07）

本节消解历史上「多名一物 / 一名多义 / 愿景与 schema 不一致」。**新代码与新文档必须按此执行**；开发阶段迁移要彻底，不留 `assistant` kind 等历史兼容层。

### 0.1 实体骨架（裁决版）

```
Workspace（API/类型真名）= Project（产品对外名）
  · 同一 id；目录投影 = workspace path
  · kind ∈ { workforce | project }     ← 落库仅两档
  · UI 文案：kind=workforce →「助理」；kind=project →「项目」

  └── ProjectItem（表 project_items；原 tasks）
        · ItemType ∈ { task | requirement | bug | discussion }
        · 仅 ItemType=task 进入 executor 调度
        · executor ∈ { agent | function | human }   ← 通道
        · assignee = 该通道下的具体对象             ← 对象
        · function 通道另保留 function_type 字段
        └── Session（chat | terminal；+ acp/cc 运行时 id）
```

### 0.2 ProjectItem / ItemType（原 tasks / TaskType）

| 裁决 | 说明 |
|------|------|
| 表名 | `tasks` → **`project_items`**（逻辑名 ProjectItems）**（待迁移）** |
| 类型名 | 前端/文档主类型 **`ProjectItem`**；不再把「Task」当表名或主类型名 |
| 枚举名 | `TaskType` → **`ItemType`** **（待迁移）** |
| 枚举值 | 保留 **`task` \| `requirement` \| `bug` \| `discussion`** |
| **强制** | **`task` 只作 ItemType 枚举值**，不再作表名、不再作 Go/TS 主类型名 |
| 可调度 | **仅 `ItemType=task`** 进入 executor 调度；requirement/bug/discussion 为不可执行议题类 |
| 话题语义 | ProjectItem 可带 Description + Replies 时间线（原 issue-model）；`issue_state` 与 workflow `status` 正交 |

### 0.3 项目从属（可无 PM 外壳 ≠ 可无存储行）

| 裁决 | 说明 |
|------|------|
| 逻辑 | 可无完整 PM 外壳（无强制里程碑/需求池等）——如 **助理 (workforce)** |
| 存储 | **每条 ProjectItem 始终挂一条 Workspace/Project 行**（含 builtin 助理） |
| 否决 | 「Task 可脱离 Project、schema 无 project_id」——与实现不符，废止 |

### 0.4 Workspace.kind 两档 + 创建向导

| 概念 | 代号 | 说明 |
|------|------|------|
| 落库 kind | **`workforce` \| `project`** | **仅此两档** |
| 历史值 | `assistant` | **彻底迁移为 `workforce`**；写路径只写新值，不做长期双读兼容 **（待迁移）** |
| UI 文案 | **「助理」** | **保持不变**（中文 UI 不因 kind 改名而改文案） |
| 创建：助理 | → `kind=workforce` | 轻量对话单元，默认可无完整 PM 外壳 |
| 创建：普通项目 | → `kind=project` | 选目录/建项目，无模板脚手架 |
| 创建：模板项目 | 向导名 **`template_project`** | **不是 kind**；创建时按模板脚手架复制到 `kind=project` 行 |

```
创建 UX
  ├─ 助理        → kind=workforce
  ├─ 项目        → kind=project（无模板）
  └─ template_project → kind=project + scaffold(template) 复制目录/配置/专家等
```

**否决**：把 `professional-project` / `generic-project` / `SessionTier` 三档当成落库枚举。  
创建向导若保留分档，模板路径统一叫 **`template_project`**。

### 0.5 executor（通道）× assignee（对象）

| 字段 | 含义 |
|------|------|
| **`executor`** | 三态**通道**：`agent` \| `function` \| `human`（字段名保持 `executor`，不改为 AIWorkforce） |
| **`assignee`** | 该通道下**具体执行对象** |

| 通道 `executor` | `assignee` 填什么 | 独立字段 |
|-----------------|-------------------|----------|
| `agent` | AgentType：`codex` / `claude` / … | 无 |
| `human` | 暂固定 **`user`**；以后可拓展员工工号 | 无 |
| `function` | function **函数名**（与注册名对齐） | **保留**现有 `function_type` / `FunctionType`（与 assignee 对齐使用；迁移期以代码约定为准） |

**否决**：

- 把 `executor` 写成唯一「谁来做」而忽略 assignee  
- 把 `executor=agent` 改名为 `AIWorkforce`（与 kind 撞车）  
- 把 Chat 消息角色 `assistant_text` 与 kind/workforce 混称

### 0.6 Project vs Workspace 命名

| 层 | 名称 | 说明 |
|----|------|------|
| 产品 / UI（项目侧） | **项目** | 对外主名；助理侧 UI 仍叫 **助理** |
| API 路径与字段 | **`workspace_*`** | 保持：`workspace_id`、`workspace_path`、`/api/...` 等 |
| 前后端类型名 | **`Workspace`** | 响应体与 `frontend/packages/core` 类型保持 `Workspace`，**避免**再引入并行 `Project` 类型导致双名 |
| 身份 | **同一 id** | `Workspace` = Project 的目录投影；`projects` 表与 API Workspace **同一套 id** |
| 文档写法 | 「项目（Workspace）」 | 首次出现可并列，之后可单用其一 |

### 0.7 Agent 一词拆义（禁止混用）

| 含义 | 正确叫法 | 代号 |
|------|----------|------|
| Workspace 形态（原 assistant kind） | **助理**（UI）/ workforce（代码） | `kind=workforce` |
| 执行通道 | **agent 通道** | `executor=agent` |
| 具体运行时 | **Agent 类型** | `assignee=codex` 等；`AGENT_REGISTRY` |
| 预置 persona 包 | **专家** | template `agents/*.md` + 绑定 skills（§0.8） |
| Chat 消息模型侧 | **assistant 消息** | `assistant_text`（**不改**） |

### 0.8 专家（Expert）

| 裁决 | 说明 |
|------|------|
| 是什么 | **预置 template agents**：`agents/*.md`（**Markdown 正文 = prompt**，元数据为 **YAML frontmatter**，不是整文件纯 YAML） |
| 带什么 | 声明/绑定的 **1skills**（技能包 / MCP / slash） |
| 何时用 | 选用某专家时，向**对应项目目录**注入 `agents/*.md`，并同步技能包 / MCP / slash |
| 与 AgentType | **正交**：专家 = persona+技能包；AgentType = claude/codex 等运行时（`assignee`） |
| 与 template_project | 模板脚手架可**打包**专家与目录骨架；创建 `template_project` 时一并复制 |

### 0.9 应用扩展（过渡期）

| 裁决 | 说明 |
|------|------|
| 远期 | agentsOS 多应用 + registry + 三挂载（project-tab / l1-page / lens） |
| **当前过渡** | **不实装** App Registry；扩展优先 **skill + scripts + 内置浏览器预览** |
| 首批 media/CRM/电台 | **弱化**：不以一等注册应用交付，能力用过渡手段承载 |
| 文档 | 旧「首批应用 / 挂载点」标为**远期**，非当前真源 |

### 0.10 连接拓扑（Remote Agent · Relay · 渠道）

三条**正交**轴，不可混称：

```
                    ┌── C1 UI（浏览器 / Tauri）
                    │
     接入方式 ──────┼── Direct：C1 → 本机 Go（如 :38080）
                    │
                    └── Relay（happy-server）：C1 ⇄ S ⇄ C2(adapter + Go + ttyd)
                              「远程连到哪台跑 1agents 的机器」

     消息渠道 ────── cc-connect：飞书 / Telegram / Discord / … ⇄ 同一 C2 上的会话/Agent
                              「工作从哪个 IM 进出」—— ≠ Relay

     Remote Agent ── 产品/历史统称：可远程操作的 Agent 工作台形态
                      = Direct 或 Relay 之上的 1agents，可再挂「渠道」
```

| 名称 | 一句话 |
|------|--------|
| **Relay** | 远程到达**哪台电脑**上的 1agents |
| **渠道** | IM/消息从**哪条业务通道**进系统（cc-connect） |
| **Remote Agent** | 整机产品/历史叫法，**不是**第三套协议 |

## 3. 领域模型

```
Workspace / 项目（同 id；kind=workforce|project）
  └── ProjectItem（project_items）
        ItemType = task | requirement | bug | discussion
        └── Session（chat | terminal）
```

| 中文名 | 代号 | 定义 |
|--------|------|------|
| **项目** | 产品名 | 对外称呼；API/类型见 **Workspace** |
| **工作区 / Workspace** | `Workspace`、`workspace_*` | **类型与 API 真名**；= 项目的目录投影，**同一 id** |
| **kind** | `workforce` \| `project` | 落库两档；UI：助理 / 项目 |
| **助理** | UI 文案 | `kind=workforce` 的 Workspace；**文案不改为英文** |
| **ProjectItem** | `project_items` | 项目工作项主实体（原 tasks 表行）**（待迁移）** |
| **ItemType** | `item_type` | `task` \| `requirement` \| `bug` \| `discussion` |
| **task（枚举值）** | `ItemType=task` | **仅枚举值**；可执行工作项；**不是表名/主类型名** |
| **需求 / 缺陷 / 讨论** | requirement / bug / discussion | 不可执行议题类；可被拆成 `task` 或 link 约束 |
| **议题状态** | `issue_state` | `open` \| `closed` |
| **工作流状态** | `status` | pending / queued / running / completed / failed / cancelled / blocked / not_ready … |
| **executor** | `executor` | 通道：`agent` \| `function` \| `human` |
| **assignee** | `assignee` | 通道内对象：AgentType / `user` / function 名 |
| **function_type** | `function_type` | function 通道注册键；与 assignee 对齐保留 |
| **Reply** | replies | ProjectItem 时间线评论/回写 |
| **Session** | chat \| terminal | 可恢复交互；可软关联 item |
| **里程碑** | Milestone | 路线图节点 |
| **meta.db** | `~/.1agents/meta.db` | 全局元数据库 |
| **business_ref** | `business_ref` | 域对象绑定：`<ns>:<对象>:<主键>`（远期应用/过渡脚本均可） |

### 易混对照

| 说法 | 正确理解 |
|------|----------|
| 工单 | **弃用** → 说 ProjectItem / 工作项；可执行的叫「task 型条目」 |
| Project vs Workspace | **同一实体**：产品「项目」，类型/API `Workspace` |
| Task 表 | **不存在** → `project_items`；`task` 只是 ItemType |
| Task vs Issue | 旧说「Task=Issue」→ 现为 **ProjectItem + 话题字段**；类型靠 ItemType |
| 助理 vs assistant_text | **助理** = workforce 实体；**assistant_text** = 模型回复气泡 |
| SessionTier / professional-project | **废止为落库概念** → 创建用 `template_project` |

## 4. 执行通道与指派

| 中文名 | 代号 | 刚柔 | 定义 |
|--------|------|------|------|
| **agent 通道** | `executor=agent` | 柔 | LLM 智能体；`assignee` = AgentType（codex/claude/…） |
| **function 通道** | `executor=function` | 刚 | 确定性程序；`assignee` = 函数名；**保留** `function_type` |
| **human 通道** | `executor=human` | 裁 | 真人决策；`assignee` 暂固定 `user` |
| **Verifier** | verifier | — | 验收门禁（实现完整度见专题 Status） |
| **PMO / PM** | PM 会话等 | — | 收口与拆项；可走专用会话角色 |
| **下沉原则** | — | — | 能 function 不 agent，能 agent 不 human |

**Agent 类型**（运行时，≠ executor，≠ kind）：见 `modules/1acp` `AGENT_REGISTRY`（claude、codex、gemini…）。默认常为 `codex`。

## 13. 产品闭环用语

| 用语 | 定义 |
|------|------|
| 工作进入系统 | Inbox / IM / 数据源 / 手动 → ProjectItem 或 Workspace |
| 系统组织工作 | 里程碑、依赖、计划、验收（PM 外壳；workforce 可弱化） |
| 执行者完成工作 | `executor` × `assignee` |
| 结果形成闭环 | 回写时间线 + status / issue_state |
| 信息漏斗 / 环路 / A2A / 时时留痕 | 理念层，见项目介绍 |
