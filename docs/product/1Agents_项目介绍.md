# 1Agents：一万-Agent Infra，搭建自循环的智能体 Graph

**1Agents 是一个开源、自托管的 AI-native 工作操作系统。**

它不是一个更大的 Chat 面板，也不是把多个 AI 助手简单放进同一个界面，而是一套面向多智能体协作的 **Agent Infra**：把数据、需求、任务、上下文、执行者、验证和状态回写连接成一张持续运转的工作 Graph，让一件工作从进入系统开始，就能够被接住、理解、拆解、调度、执行、验收，并将结果沉淀为下一轮行动的上下文。

“一万-Agent”不是对同时运行数量的机械承诺，而是对基础设施能力的定义：**执行者可以不断增加、模型可以随时替换，但承载目标、状态、依赖和验收标准的工作 Graph 必须保持稳定。**

这也是 1Agents 所说的“一人成军”：

> 一个人负责定义目标、做关键判断和承担最终责任；一组 Agent、确定性程序和自动化流程围绕同一张工作 Graph 持续推进。

---

## 1. 为什么核心是 Graph，而不只是 Loop

Loop 只能描述“执行一次，再来一次”。真实工作却不是单线程循环，而是由大量相互关联的对象和决策组成：

- 一个用户反馈可能关联多个需求；
- 一个需求可能拆成多个功能点和交付任务；
- 多个任务可以并行执行，也可能存在前置依赖；
- 一个里程碑需要等待一组任务共同完成；
- 一次验收可能通过、失败、阻塞，或者要求带着原因返工；
- 执行结果会改变项目状态，并成为后续任务的新上下文。

因此，1Agents 用 Graph 表达工作：

- **节点（Node）**：数据、Inbox 项、需求、缺陷、功能点、任务、里程碑、会话、产物和验收记录；
- **状态（State）**：待整理、已规划、待执行、执行中、阻塞、待验收、已完成或需返工；
- **边（Edge）**：来源、归属、依赖、拆解、分发、关联、验收和回写关系；
- **判断（Decision）**：依赖是否满足、任务由谁执行、验收是否通过、下一步走向哪个节点；
- **回流（Feedback）**：执行结果、失败原因、用户反馈和验证记录重新进入 Graph，更新计划并触发后续行动。

**Loop 是 Graph 中的一条回路；Graph 才是完整工作的组织方式。**

## 2. 一条从数据进入到验收回写的业务 Graph

1Agents 的核心业务链路可以分为四个阶段。

### 2.1 数据进入与治理

工作首先从真实世界进入系统：

- 接入外部数据源、IM、消息、联系人、URL、文件、日程和业务应用对象；
- 按数据源和账号保存原始数据；
- 对数据进行清洗、融合、结构化和治理；
- 通过 Python 脚本或确定性任务执行数据处理与热更新；
- 保留治理表、依赖关系和执行记录，为后续节点提供可信上下文。

数据接入的目标不是建立一个孤立的数据仓库，而是让外部信息能够继续流入项目和任务 Graph。

### 2.2 Inbox 分类与意图识别

治理后的数据和外部信息首先进入 Inbox。Inbox 是工作进入系统的统一收口层，负责：

- 聚合来自不同渠道的信息；
- 识别内容类型和用户意图；
- 区分需求、反馈、缺陷、线索、提醒和一般信息；
- 提取真实用户、问题背景、目标和约束；
- 将有价值的信息分发到对应项目，形成需求或反馈卡片。

Inbox 解决的是“哪些信息值得进入工作系统，以及它们应该去哪里”的问题。

### 2.3 任务蓝图与执行计划

需求进入项目后，不会直接变成一串扁平待办，而是被纳入 **任务蓝图（Task Blueprint）**。

任务蓝图连接：

```text
来源数据 / 用户反馈
        ↓
需求 / 缺陷
        ↓
模块 / 功能点
        ↓
交付任务 / 子任务
        ↓
里程碑 / 目标版本
```

在这张蓝图中，系统可以继续补充：

- 任务描述和验收标准；
- 负责人和执行者类型；
- 优先级、计划时间和触发时间；
- 父子任务、前置依赖和并行关系；
- 里程碑、目标版本和项目阶段；
- 关联会话、文件、代码变更和交付产物。

项目中的“功能蓝图”视图负责展示模块、功能点、来源需求和交付任务；任务、看板、日历和里程碑视图则从不同角度消费同一张工作 Graph。它们不是彼此割裂的清单，而是同一套节点和关系的不同投影。

### 2.4 调度、执行、验收与回写

当蓝图被拆解成明确的执行点后，Schedule 和任务调度机制开始推动 Graph：

1. 检查计划时间、定时规则和前置依赖；
2. 为满足条件的任务获取执行权；
3. 根据任务属性选择 Agent、function 或 human；
4. 通过 1ACP / ACPX 协议通道把任务上下文分发给 Codex、Claude Code 或其他 ACP-compatible Agent；
5. 执行者在真实工作区中使用终端、文件、Git、浏览器和工具完成任务；
6. 将过程事件、回复、代码变更和产物写回任务时间线；
7. 根据验收标准执行自动化或人工 Check；
8. 验收通过则关闭任务并推进后续节点；验收失败则携带原因回到对应节点返工；
9. 任务状态、里程碑进度和项目蓝图实时更新。

至此，一条完整链路形成：

```text
数据源
  → 数据治理与热更新
  → Inbox 分类与意图识别
  → 需求 / 反馈卡片
  → 任务蓝图
  → 待办与里程碑
  → Schedule 调度
  → 1ACP 分发
  → Agent / Function / Human 执行
  → Check 验收
  → 关闭或返工
  → 状态与结果回写任务蓝图
```

这不是一个需要人不断手动唤醒下一步的工具链，而是一张由状态和判断驱动、能够持续向前推进的工作 Graph。

## 3. 任务蓝图：产品的核心工作地图

传统任务清单只回答“还有什么没做”。任务蓝图需要同时回答：

1. **这项工作从哪里来？**
   它来自哪条数据、哪位用户、哪个反馈、需求或缺陷。

2. **它在整个产品中处于什么位置？**
   它属于哪个项目、模块、功能点、里程碑和目标版本。

3. **它与其他节点有什么关系？**
   它依赖谁、阻塞谁、由什么拆解而来，又会触发哪些后续任务。

4. **它现在是什么状态？**
   是否已规划、已拆解、执行中、待验收、被阻塞、需要返工或已经交付。

5. **谁负责完成它？**
   是交给 Agent、确定性 function，还是需要 human 做最终判断。

6. **完成的证据是什么？**
   验收标准、会话记录、工具事件、文件、代码 diff、测试结果和最终产物都应能够被追溯。

因此，任务蓝图既是规划工具，也是调度索引、状态看板和项目事实地图。Agent 数量越多，越需要所有执行者围绕同一张蓝图工作。

## 4. 产品架构：四层共同维护一张工作 Graph

| 层级 | 核心职责 | 主要对象与能力 |
| --- | --- | --- |
| **入口与数据层** | 接住外部世界的信息，并把它转换为可处理的工作信号 | 数据源、数据治理、Python/function、IM、联系人、消息、Inbox、日程、应用业务对象 |
| **组织与 Graph 层** | 保存目标、上下文、状态和关系，决定下一步应该做什么 | Project / Workspace、需求、缺陷、Task、依赖、任务蓝图、里程碑、计划、验收标准 |
| **调度与执行层** | 根据状态和规则选择执行者，并为执行提供真实工作环境 | Schedule、任务调度、1ACP / ACPX、Agent、function、human、终端、文件、Git、浏览器、Skills、MCP |
| **验证与回写层** | 检查结果、处理返工、更新状态并沉淀可追溯事实 | Check、Verifier、任务时间线、会话、产物、测试、状态变更、项目动态、Dashboard |

四层不是四套独立系统，而是围绕同一组 Graph 节点协作：入口层创建节点，组织层建立关系，执行层推动状态，验证层决定下一条边并把结果写回。

## 5. 三类执行者，共用同一个任务内核

不是所有工作都应该交给大模型。1Agents 在同一个任务 Graph 中调度三类执行者：

### Agent：处理判断、组织和变通

适合开放性任务，例如研究、规划、代码实现、故障分析、内容创作和跨工具协作。Agent 可以读取上下文、使用工具、形成方案，并根据环境状态调整行动。

### Function：处理固定、确定和可复现的步骤

适合数据转换、定时同步、构建、测试、TTS、格式转换和其他能够明确编码的流程。Function 的优势是稳定、低成本和可验证。

### Human：承担目标、取舍和最终责任

人在系统中不是被排除，而是位于关键决策节点：定义终点、批准高风险操作、处理价值判断、确认验收结果并承担最终责任。

三类执行者共享任务描述、上下文、权限、状态、验收标准和时间线，因此可以相互接力，而不需要依赖人工复制粘贴信息。

## 6. 1ACP：让执行者可替换，让工作 Graph 保持稳定

1Agents 通过 **1ACP / ACPX** 接入 Codex、Claude Code、Pi、OpenClaw 和其他 ACP-compatible Agent。

协议层提供统一、结构化的执行通道，用于传递：

- 工作目录和项目上下文；
- 任务描述与验收标准；
- 会话和连续执行状态；
- 权限模式与工具调用；
- 增量输出、执行事件和最终结果；
- 取消、恢复、重试和异常处理。

这意味着系统不需要把核心工作流绑定在某一个模型或某一个 CLI 上。执行者可以升级和替换，任务 Graph 仍然保存稳定的目标、依赖、状态和历史。

## 7. 统一工作台：Graph 的可操作界面

1Agents 将 Graph 落在一个可实际工作的 Web / Desktop workbench 中：

- 项目和工作区提供稳定的上下文边界；
- 会话与任务相互关联，讨论不再漂浮在项目之外；
- 终端、文件、Git 和内置浏览器提供真实执行环境；
- 需求、任务、看板、日历、计划和里程碑展示不同维度的项目状态；
- 数据源、联系人、消息、Inbox 和渠道持续向 Graph 提供外部信号；
- Skills、Subagents、Commands、MCP、Hooks、Plugins 和 Kits 扩展 Agent 能力；
- Dashboard 汇总项目进度、团队运行状态、任务和最近活动；
- 本机直连、Relay 和自托管部署让工作数据与执行环境保持可控。

统一工作台的价值不是“功能都在一个页面里”，而是让不同功能操作同一套项目上下文和 Graph 状态。

## 8. 1Agents 最终解决什么问题

传统 AI 助手解决的是一次对话中的单点效率；1Agents 解决的是一件工作如何持续走到被验证完成。

它带来的变化包括：

- **减少保姆式管理**：不再由人逐步复制上下文、唤醒工具和追问结果；
- **让复杂工作可拆解**：需求、任务、依赖和里程碑形成清晰结构；
- **让多 Agent 可协作**：不同执行者围绕同一组节点、状态和验收标准工作；
- **让卡点显式暴露**：阻塞、失败、缺少依赖和待确认状态能够被系统识别；
- **让结果可追溯**：每次讨论、执行、工具调用、代码变更、验证和返工都有来源；
- **让经验可以复用**：已完成任务的上下文、流程和验证结果能够成为下一轮工作的输入；
- **让人保持最终控制**：系统负责持续推进，人负责目标、边界和关键判断。

## 9. 我们的愿景：一个人，也能组织一支持续工作的 AI 团队

1Agents 面向独立开发者、单干创始人、自由职业者、知识工作者，以及需要同时推进多个项目和复杂信息流的人。

我们的目标不是制造更多需要人照看的 AI 助手，而是提供一套可以承载大量 Agent 的工作基础设施：

> 数据能够进入，需求能够被理解，复杂目标能够被拆解，任务能够被调度，执行能够被验证，结果能够回到计划。

当节点、状态、判断与回流被系统化，Agent 才能从“会做一步”升级为“持续把事情做完”。

**一万-Agent Infra，是基础设施；自循环智能体 Graph，是它的工作方式；一人成军，是它最终带给人的结果。**
