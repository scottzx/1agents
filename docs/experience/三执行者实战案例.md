# 三执行者实战案例(agent / function / human 的经验沉淀)

**Status:** Reference · 经验沉淀(认知,非实现规格)
**Author:** scottzx + Claude
**Date:** 2026-06-29
**Scope:** 产品哲学 / 架构决策依据;支撑 [agentsOS 架构设计](../agentsOS-架构设计.md) §3 固化、§6 执行层

> 这些是我们在真实使用中踩出来的案例。它们共同支撑一个判断:**确定的活下沉给 `function`(刚),需判断的交给 `agent`(柔),需担责的留给 `human`(裁);能固化的随时间从柔固化成刚。**

## 案例 1 · 批量装机:agent 幻觉把脚本掐了

**背景**:写好一套安装脚本,在 50–60 台远程机上批量装环境,一台耗时 30–60 分钟(环境问题多)。让 agent 去"在某 IP 上跑这个脚本"。

**发生了什么**:提示词里**明确写了"会很久,约 30 分钟"**,但 agent 跑到 ~10 分钟就自己推理"是不是太久了?"——**把脚本掐掉**。结果装一半、不知道哪台成了哪台没成,还得人介入引导它去查、去返工,白烧一堆 token;最后仍有 2–3 台没装成,反复重装。

**暴露的问题**:agent 在一个**确定、固定、长耗时**的流程里掺和,幻觉导致执行不稳——四十几台成功证明它"大概率能成",但**收不住那两三台异常**。

**沉淀的原则**:
- **确定的固定流程,别让 agent 在执行里参与**——脚本写好、跑通过,就该 function 刚性跑。
- **agent 规划,function 落地**(尤其长流程、关键动作)。
- 类比:写文章**复制粘贴**绝不出错别字;**对着手打**就保不齐漏字。确定的东西要"复制粘贴",不要"重打一遍"。

## 案例 2 · lark-cli 群消息聚合:固化阶梯的活样板

**背景**:要把飞书群的消息和联系人定时抓下来做分析。

**怎么走的**(三轮固化):
1. **对话探索(发散)**:在对话里让 agent 试 `lark-cli` 有哪些参数、哪些数据取得到、怎么分页。
2. **收敛成方案**:确认了"**翻页全量**拿满(突破单页封顶)+ **增量获取**(只取上次时间之后)"两条需求。
3. **固化落地**:固化成脚本 → 代码 → 聊天人模块 + 前端展示。从此**定时跑、不再每次劳烦 agent**。

**沉淀的原则**:
- **固化阶梯**:即兴对话 → skill/工具 → 定时(recurring)→ 纯代码(function)。停在哪一级,看 频率 × 稳定 × 可靠 × 成本。
- **人 → agent → 代码** 的下沉:重复 ≥2 次的活就该往下沉一级。
- 收益直接:**省 token + 刚性 100% 执行**。

## 案例 3 · 光伏电网调度:观测→分析→决策→执行 的闭环

**背景**:园区综合能源,要根据光伏发电电流/功率/发电量决定何时发电/储能/放电。

**闭环怎么跑**:
- **观测**:`function` 定时轮询 API 取遥测(固定动作,0 token);极度异常时 function 直接兜底应急(fast-path,不上 agent)。
- **分析**:`agent` 分析 + 建模 → 产出调度**策略**。
- **决策**:`human` 选用哪个策略(担责)。
- **执行**:策略一旦验证可靠,运行时由 `function` 按**判定依据**经 MQTT 直接控设备开/关——**不再过 agent**(物理 actuation 不可逆,排除幻觉)。

**沉淀的原则**:
- **策略 = 柔固化为刚**:agent 探索 + human 拍板,把"什么情况开/关"固化成"判定依据 + 逻辑代码";固化策略本身是一个**开发任务**(可能含 MQTT 联调)。
- **关键 / 物理 / 不可逆动作必须 function**:agent 永不直接 actuate 关键系统,只产策略。
- **function 有 fast-path 反射弧**:极度异常直接应急,不进"分析"。

## 案例 4 · 商机线索 / CRM:三角色按确定性分流

**背景**:群里天天刷过几千条消息,藏着商机/人脉,一个人盯不过来。

**闭环怎么跑**:
- `function`:lark-cli 取群 + 脚本清洗(刚、0 token)。
- `agent`:分析清洗后的数据,提取潜在商机线索 → 出决策卡。
- `human`:看卡决策**跟 / 弃**。
- 跟进若是开放性工作(写方案、开发 APP),则由 `agent` **柔性执行**(无关键 actuation、产出可评审)。

**代码印证**(已落地):`digest.PrepareBatch` 是"**确定性半段、无 LLM**"(= function);`digest.CreateAnalysisTask` 把分析当**任务**送进 Scheduler+TaskRunner 跑(= 任务层 → agent),价值提取作为 Reply 落到任务时间线(= 决策卡)。

**沉淀的原则**:
- **同一闭环,执行角色由"决定的动作确不确定"分流**:确定且关键 → function;开放且可评审 → agent。
- 这正是案例 1 的反面:固定的"取+洗"压给 function,只在"分析"这步用 agent。

## 案例 5 · ffmpeg 剪辑:同一能力,两种角色

**背景**:口播视频要剪辑。

**两种情形**:
- **时间戳明确**(去掉 0:04–0:09):是一个 `function` 任务,确定性执行,~0 token。
- **跨多素材组织取舍合并**:是 `agent` 手里的**工具**——agent 推理"留哪几段、怎么接",**多次 call ffmpeg**。

**沉淀的原则**:
- **角色是任务的属性,不是工具的属性**:同一个 ffmpeg,既能当 function 任务,也能当 agent 的工具。
- **别把灵活编排硬写成"剪辑程序"**——那只是把复杂度搬进脆弱代码,等于造了个残废的 agent。**function 注册表一份注册、两种消费**(独立任务 + agent 工具)。

## 总原则(从五个案例收敛)

1. **下沉到能胜任的最便宜角色**:确定 → function、需判断 → agent、需担责 → human。
2. **agent 规划,function 落地**;关键/不可逆动作绝不交给会幻觉的 agent。
3. **柔会随时间固化成刚**:探索过、验证过的活,沉淀成 skill → 定时 → function/策略。
4. **角色看任务不看工具**:同一能力按"这件事确不确定"在 function / agent 间分流。
5. **省 token + 刚性可靠**,是固化的两个直接收益,也是我们区别于"纯 agent 框架"和"纯 workflow 低代码"的根本。
