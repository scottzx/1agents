# agentsOS 架构设计 — 任务内核 · 项目外壳 · 可装可卸应用

> 1agents 以**工作 Graph** 作为当前产品内核，以「AI-native 组织 / 可组合多应用平台」作为架构外壳。
> **术语权威**：[名称定义表 §0](../product/名称定义表.md)（冲突时以名称定义表为准，本文不另造名）。
> 可调度工作单元 = **ProjectItem** 中 `ItemType=task` 的条目（口语可称「任务」）；**工单**弃用。主实体类型名是 ProjectItem，不是 Task。
> **工作 Graph / 任务蓝图**是对 ProjectItem、依赖、里程碑、调度、执行记录和验收回写的产品级组织方式，不新增平行领域实体或 `graph` 表；定义见[项目介绍](../product/1Agents_项目介绍.md)与[名称定义表 §1](../product/名称定义表.md)。
> **当前实现边界**：编译期 App Registry、Manifest 查询与启停、前端视图注册，以及 `project-tab` / `l1-page` / `lens` 三类挂载基础设施已经落地；当前生产注册应用确认到**圆桌讨论**（`agents-roundtable`）。media / CRM / 电台仍是领域应用示例，完整外部 SDK、运行时热安装与应用市场仍在演进（名称定义表 §0.9）。
> **v1.0.0 演进**：WorkCase、Command/Query/Event、Capability Contract、领域所有权、三套 Product Shell、售前闭环和电商泛化验证以[企业工作底座 v1.0.0](./enterprise-foundation-v1.0.0.md)为目标规格。本文继续描述当前已落地架构和既有概念，二者冲突时先区分“当前事实”与“目标设计”。

---

## 1. 愿景与定位

把 1agents 从「任务驱动的智能体工具」演进为一套以工作 Graph 为运行内核的 **AI-native 组织操作系统**：

- 用 ProjectItem、依赖、状态、里程碑和验收记录表达工作节点与关系；
- 把可执行工作派给 **agent**、**确定性程序（function）**或**真人（human）**；
- 通过 Schedule 与 1ACP 在一条带上下文、权限、验收和成本归属的执行脊柱上统一调度；
- 将执行与验证结果写回工作 Graph，决定关闭、返工或后续节点；
- 业务应用复用整套智能体架构，**只开发业务逻辑，AI 能力按需以任务形式调用**，不重复造 agent。

**一个产物,两种角色**
- 对内(本体):应用是**扩展单元**——平台用自己的项目/任务系统造新应用(dogfooding 自举)。
- 对外(交付):应用是**交付/商业单元**——给客户的是「核心(任务内核 + 项目外壳 + agent 后台)+ 选购的应用」固定版本。
- org 映射:**核心 = 公司 OS 内核(数字劳动力引擎,永远出厂)**;**应用 = 部门/能力(可组合可售卖)**。

## 2. 分层架构

```
┌──────────────────────────────────────────────────────────────┐
│ ① 业务层    应用 / 专业模板(自媒体 · CRM · AI电台 · 研发/Bug)    │
│            域逻辑 · 自定义视图 · function 实现 · 域表 · 配置预置   │
├──────────────────────────────────────────────────────────────┤
│ ② 项目管理层(通用项目外壳 · 内核)                              │
│            workspace(目录) · 动态/计划/任务/资产 · 项目配置       │
├──────────────────────────────────────────────────────────────┤
│ ③ 任务层(任务引擎 · 内核 · 基本要素)                           │
│            任务模型 · executor 三态 · 调度/依赖/重试/周期         │
│            verifier · 事件引擎 · 成本计量                        │
│            北向 任务 API ↑                南向 派发 ↓            │
├──────────────────────────────────────────────────────────────┤
│ ④ 执行层(三条道)                                              │
│   agent → ACP / 1acp 在 cwd 起智能体                            │
│   function → 确定性 worker(ffmpeg / 规则 / 调外部业务系统)       │
│   human → 决策 UI / 任务队列                                    │
└──────────────────────────────────────────────────────────────┘
   贯穿:存储面(meta.db 元数据 · workspace 目录 产物) · co-pilot 对话入口
```

**逐层是什么**

| 层 | 是什么 | 内核 / 应用 |
|---|---|---|
| **① 业务层** | 注册应用、专业模板或轻量扩展承载的领域能力；自媒体 / CRM / 电台为示例，不代表已经注册交付 | 应用 / 扩展 |
| **② 项目管理层** | 通用项目外壳:workspace + 动态/计划/任务/资产 + 项目配置;**组织任务** | 内核 |
| **③ 任务层** | 任务引擎:平台**基本要素**;任务模型 + 调度/依赖/verifier + 北向 API | 内核 |
| **④ 执行层** | 三条道:`agent` / `function` / `human` 把任务做掉 | 内核框架 + 应用 handler |

**层间关系**
- **③ 在逻辑上可无完整 ② PM 外壳运转**（如 **助理 `kind=workforce`**：轻量对话、无强制里程碑/需求池），但**存储上每条 ProjectItem 始终挂一条 Workspace/Project 行**（含 builtin 助理）。**否决**「任务可脱离 project / schema 无 project_id」——与实现不符，见[名称定义表 §0.3](../product/名称定义表.md)。② 坐在 ③ 之上去**组织**工作项，而非「可不挂项目行」。
- **④ 是 ③ 的派发出口**(三条道);agent 是主道,function 与 human 同层。
- **① 在 ②③④ 上生长、沉淀出来**（机制见 §3）；当前既可注册为 App Registry 应用，也可先固化为 skill / scripts / 浏览器预览。

## 3. 工作 Graph 中的固化回路（发散 → 收敛 → 沉淀）

固化是工作 Graph 中的一条重要反馈回路：**用 agent 把“不会做的”探索成“会做的”，再把“会做的”固化成更刚、更便宜、更可靠的形态。** 业务层①与专业项目模板，就是这样从 ③④ 长出来、沉淀出来的，而不是预先设计的。固化回路不替代完整工作 Graph；它消费已验证结果，并把 skill、脚本、function 或模板写回为后续节点可复用的能力。

**固化三步**:① agent 探索(发散)→ ② 收敛成方案 → ③ 固化落地。落地有不同深度,可停在任一级:

| 固化深度 | 形态 | 触发 | token | 灵活 | 适合 |
|---|---|---|---|---|---|
| **即兴** | 每次开对话让 agent 现做 | 手动 | 高 | 最高 | 一次性 / 罕见 / 模糊 |
| **工具** | agent 探索产出 skill/脚本,下次 agent 调它更快 | 手动 | 中 | 高 | 重复但需判断 |
| **定时** | 通用项目管理思想:定时跑(recurring) | 自动 timer | 看 body | 中 | 周期性 |
| **代码** | 明确固定流程 → function 代码,运行时不过 agent | 手/定/触发 | ~0 | 无 | 高频 · 稳定 · 要可靠 |

- **两轴**:过程(agent 柔 → function 刚)× 触发(临时 → 定时/事件)。
- **选择停在哪级** = 频率 × 稳定 × 可靠 × 成本。全固化收益:**省 token + 刚性 100% 执行**。
- **实例(lark-cli 取群)**:对话探索 CLI 参数 → 收敛(翻页全量 + 增量获取)→ 固化成脚本/代码/聊天人模块 + 前端。现在是(过程=function,触发=定时)。
- **自举闭环 = 固化引擎**:agent 在项目里探索 → 固化成 skill/function/模板/应用 → 装回 → 下次按固化深度运行。"固化"应是平台的一等动作。

## 4. 内核 / 应用 切线

- **内核(出厂就有)** = ②③④框架:项目外壳 + 任务引擎 + 执行层三态的槽与派发 + 北向任务 API + 南向 ACP + 存储面。
- **应用（长出来、装上去）** = ①业务层 + ④里 `function` 的具体 handler。当前支持编译期 Manifest 注册、启停和三类界面挂载；skill / scripts / 浏览器预览仍可作为更轻量的固化形态。
- 硬规则：① 应用不依赖应用；② 核心保持干净；③ Registry 是编译期模块与运行状态的边界，不等同于运行时下载安装或完整第三方 SDK。

---

## 5. 任务层(任务引擎 · 内核 · 基本要素)

- **任务模型(最小)**:id、来源应用、spec、**target(agent + cwd + 能力)**、**executor(`agent`|`function`|`human`)**、状态、结果、成本、依赖、调度/周期、回调、`business_ref`。
- PM 专属字段(编号/里程碑/issue 开关/验收/讨论)不入内核,归 `pm_*` 域表;`task` 与 `pm_*` 物理表先共存、延后拆。
- **绑定缝**:`business_ref` + `issueTasksFromBusiness` / `listTasksForBusiness`;结果经 MCP 写回应用域表。
- **北向任务 API**:应用派任务/查/回调,按应用限权。**verifier**:scheduler 自动 headless 核验。**成本**:按任务记 token。

## 6. 执行层:三角色 = 刚 / 柔 / 裁

### 6.1 定义与判据

**判据:这件事的"怎么做"定死了没有?**

| 角色 | 刚柔 | 何时用 | 例 | 成本 | 特点 |
|---|---|---|---|---|---|
| **function** | **刚** | 输入+步骤**都定死** | ffmpeg(给定时间戳)、轮询光伏 API、lark-cli 取群、清洗、**触发器** | ~0 | 可复现、可靠、不变通 |
| **agent** | **柔** | 需要**判断/组织/变通** | 多素材剪辑取舍合并、分析数据找商机线索 | token | 会推理、需 verifier |
| **human** | **裁** | 需**最终担责/定调/风险** | 是否跟进线索、金句取舍 | 人力 | 负责、稀缺、慢 |

- **角色是任务的属性,不是工具的属性**:同一个 ffmpeg,时间戳明确时是 function 任务;要跨多素材组织取舍时,是 agent 手里的工具。别把灵活编排硬写成"剪辑程序"。
- **function 注册表一份注册、两种消费**:既作独立 function 任务,也作 agent 工具。
- **依赖与调度执行者无关**,只有派发那一步按 executor 分流。
- **下沉原则**:把每件事压给能胜任的最便宜角色——确定的给 function、要判断的才上 agent、要担责的才上 human。

### 6.2 派发

- **agent**:解析 `target(agent + cwd + 能力)` → 1acp 在 cwd ensure 会话 → agent **cd 进目录执行**。
- **function**:内核出框架(注册表 + runner + 调度);应用/模板出实现(in-process / ffmpeg / 调外部业务系统如能源 SCADA、MQTT 控 IoT)。
- **human**:进决策 UI / 任务队列,等用户动作,完成解锁下游。

### 6.3 闭环与角色分布

```
观测 ──────► 分析 ──────► 决策 ──────► 执行(按确定性分流) ──────► 反馈
function     agent        human       ┌ function(刚)              └─► 回观测
采集/触发     分析/建模/    拍板选策略   └ agent(柔)
            出策略
   └─ 极度异常 → function 兜底应急(fast-path,不上 agent)
```

| 阶段 | 案例 · 光伏电网 | 案例 · 商机线索 |
|---|---|---|
| 观测 | function 轮询 电流/功率/发电量 | function lark-cli 取群+清洗 |
| 分析 | agent 分析+建模→出调度策略 | agent 析有无商机线索 |
| 决策 | human 选用哪个策略 | human 决定是否跟进 |
| **执行** | **function 刚性**:按判定依据 MQTT 控 PV 开/关 | **agent 柔性**:写方案、开发 APP |
| 为何 | 物理 actuation 不可逆,排除 agent 幻觉 | 开放性知识工作,需变通 |

**三个原则**
1. **策略 = 柔固化为刚**:agent 探索 + human 拍板,把"什么情况开/关"固化成策略(判定依据 + 逻辑代码),运行时 function 直执行。固化策略本身是一个开发任务(走自举闭环,可能含逻辑代码 + MQTT 联调)。
2. **agent 规划,function 落地**(对关键/物理/不可逆动作):agent 永不直接 actuate 关键系统,只产出策略。
3. **function 有 fast-path 反射弧**:极度异常直接兜底应急,不进"分析"。

## 7. 项目管理层(通用项目外壳 · 内核)

- **workspace** = 目录 + 身份 + 可用 agent 白名单(内核瘦概念)。任务带 `cwd = 项目目录`。
- **通用项目外壳(平台级 scaffold)**:`动态 / 计划 / 任务 / 资产` 四标签 + **项目配置**。
- **项目配置 = 该项目的 agent 上下文**:`指令`(system prompt)+`连接器`(MCP)+`专家`(角色)+`技能`+`自动化`。项目内派任务时,任务的 `target.能力 / 提示词`来自项目配置。
- **创建入口（UX，非落库三档 kind）**：见[名称定义表 §0.4](../product/名称定义表.md)——**助理** → `kind=workforce`；**项目** → `kind=project`（无模板）；**template_project**（向导名，**不是 kind**）→ `kind=project` + 模板脚手架。**否决**将 `professional-project` / `generic-project` / `SessionTier` 当作落库枚举。
- **项目模板机制**：新建模板项目 = 选模板 → 铺 workspace 子目录骨架 + 预置配置。模板脚手架与 App Registry 是可组合但不同的机制；某个领域应用是否随模板装载，以该应用的实际注册和模板配置为准。

## 8. 业务层（应用 / 专业模板）

> **状态（名称定义表 §0.9）**：App Registry、Manifest 启停、前端视图注册和三类挂载基础设施已落地；当前生产注册应用确认到圆桌讨论（`agents-roundtable`，`l1-page`）。media / CRM / 电台仍是领域示例，不能据此视为已交付应用。

**应用 = 模块 + 挂载点（Manifest 声明）**：

| 挂载点 | 呈现 | 适用 | 准则 |
|---|---|---|---|
| **项目内 tab** | 项目详情加主标签(与 动态/任务/资产 平级) | 自媒体、视频、研发/Bug | 一个项目 = 一个实例 |
| **L1 独立页** | 左侧导航独立全局页 | CRM、AI 电台、财务 | 一个全局实例,跨项目 |
| **项目透视(lens)** | 往项目/Home 叠加横切视图 | 财务(成本)、CRM(关联线索) | 横切,叠加 |

- 项目级应用**必须**做成项目内 tab(继承项目外壳);全局级做 L1 页;一个应用可多挂载点。
- **“专业模板”可组合项目模板与项目级应用；“全局应用”挂在 L1**。界面接入共用 App Registry 和挂载点机制，但模板脚手架与应用注册不是同一个实体。
- **`function` 是专业模板的核心贡献**:通用内核擅长 agent/human,缺确定性工人。模板贡献 = skills/提示词 + `function` 工人 + 自定义视图/域表 + 自动化。

**领域应用示意（非当前交付清单）**

| 应用 | 挂载点 | 骑在谁身上 | 新增 |
|---|---|---|---|
| 自媒体 | 项目内 tab | scheduler/runner + function | ContentProject 域 · 素材库(资产特化)· 素材处理混合管线 · 段落取舍 tab |
| CRM | L1 页(+透视) | Inbox intake + digest ACP | Contact/Lead 域 · 来源聚合 · 挖掘打分 · 富集 · 漏斗页 |
| AI 电台 | L1 页(opt-in·验证) | RSS + TTS | RadioEpisode 域 · 三段任务(agent + function TTS)· 音频存储串流 · 点播页 |

## 9. 三存储面 + cwd

| 面 | 存什么 | 例 |
|---|---|---|
| **meta.db** | 元数据 / 索引 / 状态 | 素材名·路径、阶段状态、任务 |
| **项目目录(workspace)** | 字节 / 产物本体 | 口播原片、音频、成片脚本 |
| **任务总线** | 只传 spec + cwd | "处理 cwd 下 clip2.mp4 的静音段" |

二进制大产物走文件面,不进任务 payload、不进 meta.db 字节。cwd = workspace 目录,1acp 在 cwd 起 agent(项目地址 = agent 的 pwd)。

## 10. 插件化与自举（= 固化引擎）

> **当前边界**：编译期 Registry、启停和三类挂载已落地；动态下载、运行时热安装和完整第三方应用 SDK 尚未因此自动成立（§0.9）。

- **当前装载机制**：应用后端模块在编译期调用 Registry 注册 Manifest，前端 bundle 注册视图，运行时可启用 / 停用。这里的开关控制可见与可用状态，不代表动态安装新代码。
- **自举生命周期（目标形态）**：需求（Inbox / 对话）→ 立项 + 项目目录 → Agent 开发 / 部署 / 测试 → CI/CD → 编译并注册回平台 → 运行时回调任务 API。应用运行时**不自带 Agent**，统一回调平台执行任务。
- **应用契约两面（SDK）**：当前已有内部 Manifest 与挂载契约；完整外部 SDK 仍按[契约草案](./app-sdk-contract.md)演进。应用侧提供 Manifest + 前端视图 + 后端模块（含 function）+ `business_ref` 命名空间；平台侧提供任务 API + 领域存储 + 共享源（Inbox / RSS / digest）+ 项目外壳 + co-pilot + 挂载点。

## 11. 企业交付形态

- **核心 = delivery floor**(任务内核 + 项目外壳 + agent 后台),每个客户都有;**应用 = 可组合可售卖**。
- **我们卖的,就是我们用来造自己的那套东西** —— 无"产品代码 / 平台代码"两套。
- 诚实:交付会更早逼出 **RBAC/多租户** 与 **on-prem 模型密钥/token 成本/合规**——设计核心契约时留位。

---

## 12. Phase 1 范围 · 北极星 · 纪律

- **当前交付重心**：单用户 · 无 RBAC · 工作 Graph + 任务内核 + 项目外壳 + executor 三态 + App Registry 基础设施 + skill/scripts 轻量扩展。圆桌讨论已注册；media / CRM / 电台不在当前已交付清单。
- **演进北极星（仍有效、非当前闸门）**：新增注册应用尽量不改内核，并逐步形成稳定的外部 SDK 与交付规范。
- **北极星(不做)**:运行时热装、多租户 RBAC、财务/成本归集/预算、第三方市场、固化一等化(一键收割)。
- **纪律**：术语与实体以[名称定义表 §0](../product/名称定义表.md)为准；可调度仅 `ItemType=task`；ProjectItem 始终挂 Workspace；应用交付状态以生产注册、前端视图和验收证据共同判断。

| 术语 | 含义 |
|---|---|
| **ProjectItem / 任务（口语）** | 主实体 ProjectItem；仅 `ItemType=task` 可调度；executor ∈ {agent,function,human} × assignee |
| **任务内核** | ProjectItem 引擎：调度/依赖/重试/周期 + verifier + 事件 + 成本 + 北向 API + 南向派发 |
| **项目外壳** | 平台级 scaffold:workspace + 动态/计划/工作项/资产 + 项目配置；可无完整 PM 外壳 ≠ 可无 project 行 |
| **workspace / 项目** | API/类型真名 Workspace = 产品「项目」；助理 UI = `kind=workforce` |
| **应用 / 专业模板** | 应用是注册进 App Registry 的模块，挂载点 = 项目内 tab / L1 页 / 透视；专业模板可组合目录脚手架、配置与应用。skill/scripts/浏览器是并行的轻量扩展形态 |
| **固化 / 核心循环** | 把 agent 探索沉淀成更刚的形态(即兴 → 工具 → 定时 → 代码) |
| **function(刚)** | executor 之一:确定性 worker;内核出框架、应用出实现;一份注册、两种消费 |
| **agent(柔)** | executor 通道之一（≠ kind=workforce 助理；≠ Chat `assistant_text`） |
| **human(裁)** | executor 之一:最终担责拍板 |
| **策略** | 柔固化为刚的产物:判定依据 + 逻辑代码;由 function 刚性执行 |
| **business_ref** | 任务到应用业务对象 / 阶段的绑定缝；具体应用按需使用 |
| **co-pilot** | 随处可唤的对话入口;意图识别 → 落成任务 |
