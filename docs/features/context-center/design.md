# 上下文中心设计方案

## 1. 背景与目标

当前“联系人”入口承载了联系人和消息两个专属页面；“数据源”则同时承担数据接入、治理和治理结果下钻。两者之间缺少一个面向使用者的数据消费层：用户能看到数据已经治理完成，却无法按业务价值挑选、组织和持续消费这些结果。

本功能将侧边栏的“联系人”替换为“上下文中心”。上下文中心只展示数据治理的输出表，并让用户勾选自己希望在首页消费的表。它面向“已治理/已融合的数据”，而不是数据接入、授权、同步或治理运维。

成功标准：

- 用户可从上下文中心进入一个卡片化的已选数据总览，并通过“管理展示”勾选可用治理表、调整首页顺序。
- 原联系人与消息入口迁移为上下文中心的内置展示器：融合联系人表呈现联系人体验，融合消息表呈现消息体验。
- 其余治理输出可稳定使用通用多维表格浏览，保持搜索、排序、分组、列显隐和记录详情能力。
- 原始 bronze 数据不可在上下文中心选择；数据接入与治理操作仍在“数据源”中完成。
- 配置在本机 `meta.db` 持久化，刷新或重启后仍可恢复。

## 2. 产品边界与信息架构

### 数据源与上下文中心的边界

| 模块 | 面向目标 | 可见数据 | 主要操作 |
| --- | --- | --- | --- |
| 数据源 | 把数据接入并治理正确 | 原始数据、治理 DAG、执行日志 | 授权、同步、运行/重跑治理、排障 |
| 上下文中心 | 消费已经治理完成的数据 | 治理输出表（silver/gold） | 勾选展示、浏览、筛选、查看记录与业务专属详情 |

上下文中心绝不读取或呈现原始 bronze 表，也不放置同步、重跑、模板安装等运维动作。治理失败、未运行或表不存在时，中心只呈现状态和引导用户返回数据源处理。

### 路由与层级

侧边栏入口和页面标题由“联系人”改为“上下文中心”。使用全局面包屑承载导航层级，避免在内容区重复放置返回控件：

```text
上下文中心
上下文中心 › 联系人
上下文中心 › 消息
上下文中心 › <治理表名称>
```

首页为卡片总览；单击卡片进入二级数据页。返回面包屑根节点即回到卡片总览。

## 3. 数据目录、选择与展示类型

### 可选择目录

后端以治理 DAG 的步骤输出为唯一数据目录来源。目录中的每一项至少返回：表名、层级（silver/gold）、业务域、记录数、最近成功运行时间、最近运行状态、上游数、用户是否已选、首页排序位置和展示类型。

选择规则：

1. 仅已注册的治理输出表可选；bronze 源表和任意未注册数据库表一律拒绝。
2. `tier=gold && domain=contacts` 使用 `contacts` 内置展示器。
3. `tier=gold && domain=messages` 使用 `messages` 内置展示器。
4. 其他输出表使用 `grid` 通用展示器。
5. 联系人和消息在首次迁移时默认勾选；用户可在“管理展示”中隐藏它们，但不能把任意表手工指定为联系人或消息展示器。

展示类型由治理元数据稳定计算，而非根据字段名猜测。这样新表先可靠进入通用表格；只有新增明确的领域展示器时才改变呈现方式。

### 配置持久化与接口

新增本机持久化表 `context_center_tables`，建议最小字段为：

```text
table_name TEXT PRIMARY KEY
enabled    INTEGER NOT NULL
position   INTEGER NOT NULL
updated_at TEXT NOT NULL
```

配置只保存用户选择与顺序；表的标签、层级、领域和展示类型始终以服务端目录为准，避免过期配置伪造可读取的数据表。

新增接口：

- `GET /api/context-center/catalog`：返回经过治理目录校验并合并用户配置后的所有可选表及摘要。
- `PUT /api/context-center/config`：原子保存已选表及位置；校验所有表都仍在目录中，拒绝 bronze 或未知表。
- `GET /api/context-center/table?name=&limit=`：初期复用现有治理输出读取逻辑；为后续聚合、分页和可视化预览保留独立演进点。

## 4. 页面与视觉设计

### 首页：工作台总览

首页以已选表的卡片墙呈现，按用户排序；未显式排序的表放在最后并按更新时间降序。联系人、消息作为优先级更高的主卡片，其他表使用紧凑的 Bento 数据卡片。

统一卡片内容：

- 标题和业务域；
- `Gold 融合` / `Silver 治理` 标签；
- 记录数、上游表数、最近成功更新时间与健康状态；
- 轻量数据预览；
- 单击进入二级页。

专属预览：

- 联系人卡片显示首字母/头像、姓名、组织或来源、最近更新时间；
- 消息卡片显示发送者、会话、最近一条消息摘要和时间；
- 通用表卡片显示关键字段示例或字段数/记录数摘要，不铺满完整表格。

首页右上角提供“管理展示”。其抽屉按“融合数据”和“治理数据”分组，表项带有层级、领域、记录数、更新时间和展示类型标签，支持复选及排序。无治理表时展示空状态并引导至数据源；无已选表时展示“管理展示”主按钮。

### 二级页：三种展示器

| 展示器 | 适用表 | 体验 |
| --- | --- | --- |
| contacts | gold + contacts | 联系人列表/卡片、来源与身份聚合、联系人详情；去除旧联系人模块中的人工新增、渠道发现、绑定与同步配置动作。 |
| messages | gold + messages | 会话式时间线、按日期分组、发送者/会话信息、消息详情；数据由融合消息表驱动。 |
| grid | 其他治理输出 | 复用通用 `DataGrid`：搜索、排序、分组、列显隐、列顺序持久化和记录详情弹层。 |

联系人和消息展示器需要以融合表行构建专用读模型；当行缺少可展示的非关键字段时使用“—”或隐藏该辅助信息，不能因此回退到旧联系人 API。若融合表暂时不可读，显示治理状态和回到数据源的引导，而非陈旧数据。

## 5. 技术实现与迁移

### 后端

1. 在 `meta.db` 迁移中创建上下文中心配置表，并实现读取、校验、保存和排序更新的 store。
2. 为 catalog 聚合治理 DAG、最后运行结果、表记录数和用户配置。目录计算必须基于真实已注册输出，不允许客户端传入任意表名。
3. 暴露只读上下文中心 HTTP handler；数据读取复用治理输出的 schema-free 行格式，避免复制 SQL/序列化逻辑。
4. 为 contacts/messages 提供或复用稳定的融合表读适配：前端只依赖展示器契约，不回读旧的联系人/会话写模型。
5. 保留现有数据源、治理 DAG、表下钻与重跑 API，避免回归数据接入流程。

### 前端

1. 将 `RightDrawerTab`、sidebar、页面标题和 `ContentViewHost` 中的联系人入口改为上下文中心；更新中英文 i18n 文案和图标语义。
2. 新建上下文中心页面状态：目录加载、管理展示抽屉、已选顺序、卡片首页、当前二级表与全局面包屑同步。
3. 复用治理卡片的数据摘要、`DataGrid`、`RecordModal` 和通用列推导；不要复制一套通用表格。
4. 将联系人/消息现有可复用的只读展示组件拆成数据适配层与渲染层，替换旧模块的独立 API 调用；同步、发现、人工编辑等写操作不迁入中心。
5. 首页卡片仅负责发现与进入；后续指标、趋势、关系图、地图或时间轴作为同一表的额外只读视图接入，不改变数据源或治理层接口。

## 6. 验收与测试

后端测试：

- catalog 只返回治理输出，拒绝 bronze/未知表配置；
- 配置新增、取消选择、重排、表被删除或不再注册时的修复行为；
- contacts/messages 的 `gold + domain` 分类正确，其他表稳定归类为 `grid`；
- 空目录、无运行记录、失败运行和表读取错误均返回可消费状态；
- 配置迁移与本机数据库重启后的持久化。

前端测试：

- sidebar/标题/面包屑均显示“上下文中心”；
- 已选卡片排序、管理展示复选、保存后刷新恢复；
- 联系人和消息走专属展示器，普通表走 `DataGrid`；
- 卡片、二级页、空状态、错误状态和返回导航的交互；
- 现有数据源接入、治理表下钻和治理运维 UI 不受回归影响。

## 7. 明确的默认决策

- 本期只展示治理输出，不支持在上下文中心勾选原始数据接入表。
- 联系人和消息以融合表为数据源，以内置专属展示器为呈现方式；不再保留旧联系人模块的并列入口。
- 首页优先是工作台卡片总览，非大表格页面。
- 展示偏好保存于本机 `meta.db`，不以浏览器缓存作为唯一来源。
- 本期不实现图表编辑器或自定义可视化；实现可扩展的页面/接口边界，为后续可视化增加只读视图。
