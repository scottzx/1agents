## 1. 背景与问题

复杂软硬件产品议题需要多职能视角碰撞。单 Agent 容易自洽、缺少对立，因此圆桌采用固定三轮剧本和六个真实独立 Agent session，提供可审计的多职能讨论。

MVP 已能跑通 R1 → R2 → R3，但现有交互把同一业务对象拆成多个无关联副本：

- 裁判在 Chat 中输出 Brief 草案；
- 用户回到圆桌后再次手工填写 Brief；
- 确认后，完整 Brief 同时出现在 system turn、房间头部和右侧栏；
- R1 裁判会话需要离开圆桌页面打开，圆桌时间线又保存一份相同对话；
- R2/R3 运行期间只有轮询和席位灯，缺少可靠的房间级进度、幂等启动和失败恢复；
- 完成态仍以长时间线为主，最终结论没有成为首屏。

这些问题使用户难以判断“当前唯一有效的 Brief 是哪一份”“本轮是否真的已经启动”“失败后应该怎么继续”。

## 2. 产品目标

把圆桌从“编排监控页 + 六个独立 Chat 入口”升级为一个**按阶段变化的讨论工作台**：

1. R1 以“与主持人澄清议题”为主，Brief 是唯一、结构化、可编辑和可确认的业务产物。
2. R2 以五个角色的独立判断和真实进度为主。
3. R3 突出各角色对上一轮观点的保留、修正和反驳。
4. 完成态默认展示最终结论、行动项和未决风险，讨论过程作为证据下钻。
5. 长任务可恢复、可重试、不可重复启动。

## 3. 产品原则

### 3.1 一个业务对象只有一个正文实例

同一页面中，Brief、Summary₂ 和 Summary₃ 各自只能有一个完整正文实例。其他位置只允许显示状态、版本、摘要、锚点或事件引用。

### 3.2 对话与产物分离

Chat 负责澄清和解释；Brief、阶段总结、最终结论是结构化产物。Agent 可以提案，只有用户可以确认 Brief。

### 3.3 当前阶段决定主界面

- R1：裁判对话 + Brief Inspector。
- R2：独立分析进度 + 五席观点 + Summary₂。
- R3：立场变化 + 交叉回应 + Summary₃。
- Done：最终结论 + 行动项 + 风险；历史讨论折叠。

### 3.4 用户语言优先

界面不暴露 `waiting_r2`、`seat cwd`、`ONEAGENTS_CLI`、`真多 session` 等实现术语。按钮描述用户动作，例如“确认议题”“开始独立分析”“开始交叉讨论”。

## 4. 用户故事

1. 作为产品负责人，我在圆桌内直接与主持人澄清问题，不需要在圆桌和普通 Chat 页面之间来回切换。
2. 作为用户，我能看到主持人维护的唯一 Brief 草案，编辑后明确确认当前版本。
3. 作为决策者，我能实时看到五个职能席位的完成、运行、失败和缺席情况。
4. 作为用户，单个席位失败时，我可以重试该席位或在明确缺席的前提下继续总结。
5. 作为复盘者，我打开已完成圆桌时首先看到最终判断、行动项和未决风险，再按需查看两轮证据。
6. 作为移动端用户，我能在“讨论 / 议题 / 参与者”之间切换，不需要操作嵌套滚动区。

## 5. 目标流程

```text
创建圆桌
  → R1 与主持人澄清
  → 主持人更新 Brief 草案
  → 用户编辑并确认 Brief 版本
  → 开始 R2 独立分析
  → 处理失败席位 / 主持人生成 Summary₂
  → 用户开始 R3 交叉讨论
  → 处理失败席位 / 主持人生成 Summary₃
  → 默认进入最终结论视图
```

### 5.1 R1 Brief

- 主持人通过结构化动作提交 Brief proposal，不再依赖 Markdown 正文传递 Brief 数据。
- Chat 中只显示“Brief 草案已更新至 vN”的紧凑事件。
- 右侧 Brief Inspector 是桌面端唯一完整 Brief 正文。
- 用户可以编辑草案并确认指定版本。
- 确认事件只显示“你已确认 Brief vN”，不在时间线复制四字段全文。

### 5.2 R2 / R3

- 启动轮次后立即进入 running 状态，不能继续显示为 waiting。
- 显示 `已完成 / 总数`、当前发言席位和失败席位。
- 每席默认展示职能、状态、一句话结论和可展开正文。
- process/tool 继续默认折叠，可按需打开底层会话。
- Summary 全文只出现在主区；Inspector 只提供状态和锚点。

### 5.3 完成态

首屏按以下优先级展示：

1. 最终建议；
2. 关键取舍；
3. 行动项及负责职能；
4. 未决风险；
5. Brief；
6. R2/R3 讨论证据；
7. 底层 Agent 会话和过程。

## 6. 功能范围

### P0：交互止血

- 删除房间头部重复 Brief 卡。
- system turn 改为紧凑事件，不显示 Brief 四字段全文。
- 圆桌内直接使用裁判 EmbeddedChat；R1 不再跳出圆桌。
- R1 对话不再同时复制为普通时间线卡。
- 精简标题区、席位状态和开发术语文案。

### P1：Brief 单一真源

- 增加 Brief 草案版本、状态、来源和确认信息。
- Agent 使用 `propose-brief`；用户通过 UI 确认。
- R2 固定使用确认版本快照。
- 明确 R2 开始后的 Brief 修改与重新讨论策略。

### P1：可靠运行

- 增加异步 RoundRun 和原子状态抢占。
- 启动接口幂等，刷新、多窗口和网络重试不会重复启动一轮。
- 提供房间级进度事件和断线恢复。
- 支持单席重试、跳过并继续、阶段总结失败重试。

### P1：阶段化工作台

- R1、R2、R3、完成态使用不同的主内容层级。
- R3 突出保留、修正、反驳和新增证据。
- 完成态以最终结论为主，历史轮次折叠。

### P2：移动端、可访问性与列表效率

- 移动端提供“讨论 / 议题 / 参与者”分段视图。
- 主操作和输入区遵守安全区并保持可达。
- 状态不只靠颜色，触摸目标不小于 44px。
- 圆桌列表突出“等待我操作”和最后更新时间。

## 7. 数据与接口要求

### 7.1 BriefVersion

最小字段：

```text
room_id
version
status: draft | proposed | confirmed | superseded
content_json
proposed_by: user | referee
source_turn_id?
created_at
updated_at
confirmed_at?
```

### 7.2 RoundRun

最小字段：

```text
id
room_id
round: 2 | 3
status: queued | running | summarizing | completed |
        partial_failed | failed | canceled
idempotency_key
started_at
finished_at?
error?
```

### 7.3 房间派生状态

房间响应应直接提供：

- `phase`
- `phase_status`
- `next_action`
- `progress.completed / total`
- `progress.active_roles`
- `progress.failed_roles`
- `current_brief.version / status`

前端不应在多个组件中自行解析底层状态字符串。

## 8. 验收

1. R1 无需离开圆桌即可完成主持人多轮对话。
2. 同一页面中只有一份完整 Brief 正文。
3. Brief proposal、编辑、确认均指向明确版本。
4. Agent 不能替用户确认 Brief。
5. Brief 确认事件不再复制四字段全文。
6. 两个客户端并发启动 R2 时只创建一个 RoundRun。
7. R2/R3 运行中可看到真实 `n/5` 进度和席位状态。
8. 单席失败可重试或跳过继续；其他已完成结果不丢失。
9. 刷新或重连后恢复同一运行状态，不需要用户猜测是否仍在执行。
10. R3 能区分席位的保留、修正和反驳。
11. 完成态默认显示最终结论、行动项和未决风险。
12. 375px 宽度下，无需嵌套滚动即可访问讨论、Brief、参与者和主操作。
13. 主 UI 默认只展示正文；tool/thinking 过程仍按需展开。
14. 关键前端组件、幂等启动、版本冲突和失败恢复有自动化测试。

## 9. 成功信号

- 用户确认 Brief 时不需要从 Chat 手工复制字段。
- 页面内不再出现多张内容相同的 Brief 卡。
- R1、R2、R3 和完成态的主任务在首屏可识别。
- 长任务刷新后仍能看到真实进度。
- 失败席位不会迫使整场圆桌从头重来。

## 10. 非目标

- 用户自定义席位数或角色拓扑。
- 多种 Agent 二进制混排。
- 无限轮讨论或动态 GroupChat。
- 投票、DAG 画布。
- 圆桌结束后自动写码、改文件或执行 Git。
- 同时嵌入五个完整 ChatUI。
