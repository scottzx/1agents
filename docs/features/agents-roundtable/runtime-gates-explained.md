# 为什么圆桌使用分层门禁

**Status:** Implemented design explanation
**Updated:** 2026-07-28
**Reference:** [《圆桌当前运行机制参考》](./runtime-reference.md)

圆桌要解决的不是“让六个 Agent 都说一句话”，而是保证一次多角色讨论在刷新、并发点击、单席失败和 Agent
输出不规范时，仍能回答四个问题：

1. 当前业务阶段是什么？
2. 哪些席位真的执行过并落下了正文？
3. 哪个正式产物已经通过授权入口提交？
4. 失败后可以重跑哪一小段，而不会重复已经完成的工作？

因此当前实现没有用一个 `status` 字段包办全部语义，而是把业务阶段、执行实例、逐席进度和正式产物分开。

## 1. 四层控制面

```text
┌─────────────────────────────────────────────────────────────┐
│ RoomState：业务阶段                                         │
│ drafting → waiting_r2 → summarizing_r2 → waiting_r3 → ...  │
├─────────────────────────────────────────────────────────────┤
│ RoundRun：某一轮的执行实例                                  │
│ queued → running → summarizing → terminal                  │
├─────────────────────────────────────────────────────────────┤
│ RunSeat：五个职能席的 at-most-once 执行门                   │
│ queued → running → completed / failed / skipped            │
├─────────────────────────────────────────────────────────────┤
│ Artifact：BriefVersion / Summary₂ / Summary₃               │
│ 只有受控写入 + runner 核验后，才允许阶段出站                │
└─────────────────────────────────────────────────────────────┘
```

### RoomState 回答“用户在哪里”

RoomState 决定页面当前展示提案、独立分析、交叉验证还是最终结论，也决定哪个主操作可见。

### RoundRun 回答“这一轮执行得怎样”

Room 进入 `summarizing_r2` 后，可能处于：

- 刚排队；
- 五席运行中；
- 等待裁判总结；
- 一个席位失败；
- 总结失败。

这些差异不能继续塞进 RoomState，否则房间状态会膨胀成几十个组合。RoundRun 把一次执行的生命周期独立出来。

### RunSeat 回答“谁完成了”

五席并行时，房间级 `running` 无法说明市场已完成、运营失败、研发仍在运行。逐席记录既提供真实 `n/5`
进度，也提供失败后的最小重试单元。

### Artifact 回答“正式结果是否存在”

Agent 的普通文本回复只能证明它说了什么，不能证明正式 Brief 或阶段总结已经落到业务数据中。产物层把“对话”
和“可供下一阶段读取的工件”分开。

## 2. 为什么采用固定三阶段

开放式 GroupChat 容易出现：

- Agent 互相点名后无限追加轮次；
- 不知道什么时候能形成结论；
- 成本无法预测；
- 一个失败席位拖死整个讨论；
- 刷新后难以恢复“谁接下来发言”。

固定流程把成本上限写死：

```text
R1：用户与裁判多轮，直到用户确认 Brief
R2：五席各 1 turn + 裁判 1 个正式 Summary₂
R3：五席各 1 turn + 裁判 1 个正式 Summary₃
```

代价是不能动态加席、投票或无限追问。当前产品选择可控和可恢复，暂不选择开放式讨论自由度。

## 3. 为什么 R2 隔离、R3 公开

如果五席在第一轮就看到彼此观点，后发席位容易沿用前面最完整的答案，最后得到五份措辞不同但判断相同的文本。

R2 因此只提供确认后的 Brief 和本席角色契约：

```text
市场 ─┐
产品 ─┤
研发 ─┼─ 相互不可见 → 五份独立判断
运营 ─┤
财务 ─┘
```

R3 才公开五份 R2 正文和 Summary₂：

```text
自己的 R2 私有历史
+ 五席 R2 公开正文
+ Summary₂
→ 保留 / 修正 / 反驳 / 新增证据
```

这样 R2 用于增加观点多样性，R3 用于检验和收敛，而不是把同一任务重复两次。

## 4. 为什么 R3 必须 resume 原 ACP 会话

只把 R2 文本重新塞给一个新 Agent 会话，会丢失本席上一轮形成判断时的私有推理上下文，也无法证明“产品席 R3”
和“产品席 R2”是同一个持续席位。

当前实现持久化 `seat.acp_session_id`，R3 使用该 ID resume：

- 身份连续；
- 本席能记住自己的 R2 历史；
- 系统只需要注入公开的跨席上下文；
- 若 ID 缺失，该席失败并进入恢复流程，而不是静默换一个新会话冒充连续性。

代价是 ACP 会话可恢复性成为 R3 前置依赖。

## 5. 为什么裁判普通回复不能开门

假设裁判在普通回复里写了“大家达成共识，可以进入下一轮”，但没有更新 `summary_r2`：

- 页面刷新后可能看不到正式 Summary；
- R3 prompt 没有稳定数据源；
- 普通 Chat Markdown 无法作为原子事务的一部分；
- 任何席位都可能伪造类似文本；
- runner 不知道总结是否完整落库。

因此 Summary₂ 和 Summary₃ 使用显式 CLI 工具：

```text
裁判生成正文
  → 调用 submit-r2-summary / submit-r3-summary
  → sidecar + store 校验身份、房间、阶段、Run
  → Summary 字段和 summary turn 同事务落库
  → runner 二次核验
  → 原子推进 Room 和 Run
```

这是一道“产物门”，不是 prompt 中的一句建议。即使模型忽略提示词并在普通回复里输出完整终稿，阶段也不会推进。

## 6. 为什么工具提交不直接改变阶段

工具只负责写产物，runner 才负责阶段转换，避免两个写入者同时拥有编排权。

如果工具直接把 Room 改为下一阶段，可能出现：

```text
Room 已进入 waiting_r3
但 Run 仍是 summarizing
或 summary turn 尚未提交
或 terminal event 尚未写入
```

当前 `FinalizeRoundRun` 把 Run terminal 状态、Room summary/state、summary event 和 run event 放在同一个事务中。
重连客户端不会看到“Run 已完成但 Room 仍停在旧阶段”的半完成状态。

工具提交后、runner finalize 前，Room 会短暂保留在 `summarizing_r2/r3`。这是有意的：产物存在不等于整个阶段已经
完成收尾。

## 7. 为什么 Room、Summary 字段和 Turn 都要保存

Summary 同时存在于：

- `rooms.summary_r2/summary_r3`：快速读取当前阶段正式产物；
- `turns(kind=summary)`：时间线归属、裁判来源和历史证据。

runner 要求两者正文一致才放行。这避免只有 Room 字段而没有来源 turn，或只有一条聊天记录却没有正式 Room 工件。

这种双记录增加了一点写入复杂度，所以工具使用事务一次完成，读取时再做一致性核验。

## 8. 为什么失败按 scope 分类

“失败”不是一种恢复动作：

| 失败位置 | 可以安全重做什么 | 不能重做什么 |
|----------|------------------|--------------|
| 单个职能席 | 只重试该席 | 其他已完成席 |
| 裁判总结 | 只重试裁判或复用已提交工件 | 五个职能席 |
| 房间 / 存储 | 先重新同步 | 在状态不明时随意启动席位 |

`error_scope=seat|summary|room` 让后端明确告诉前端该显示哪组按钮。前端不根据错误字符串猜恢复策略。

### `partial_failed` 的两个阶段

当前 `partial_failed` 需要结合 `error_scope` 解释：

1. `partial_failed + seat`：尚未完成，等待用户重试或跳过。
2. `partial_failed + none`：用户已经接受缺席，裁判总结已成功，Room 已进入下一阶段或 Done。

这保留了“本轮并非五席全成功”的审计事实，同时允许流程继续。

## 9. 为什么恢复继续使用同一个 Run

创建新 Run 会让进度、事件和已有 turn 分裂成两份，用户也无法判断哪份是当前结果。

当前恢复都使用原 `run_id`：

- 失败席原子 `failed → running`；
- 成功席的执行门保持关闭；
- 新的重试 turn 追加到时间线；
- UI 选择该席当前轮次的最新 turn；
- 总结重试只重开 summary gate。

这让恢复是“补完同一次执行”，不是偷偷发起一次新讨论。

## 10. 为什么同时保留事件和 Room 投影

Room 投影适合页面首次加载：

```text
给我当前阶段、当前 Run、当前 n/5 和可用动作
```

事件流适合增量恢复：

```text
给我 seq=37 之后发生的席位和总结变化
```

两者同时存在的原因是事件重放不能替代首次快照，而每次完整拉 Room 又比增量事件重。

当前前端仍采用 Room 轮询，事件 API 尚未接入页面。好处是实现简单、刷新恢复可靠；代价是产生周期性完整请求，且
`after/last_seq` 的断线续传价值尚未在 UI 中兑现。

## 11. 后端异步与当前前端同步等待

后端启动接口默认返回 `202 + run_id`，执行在后台继续。这使网络重试、多个窗口和刷新都可以围绕同一个持久化 Run
工作。

当前页面主按钮仍调用 `?wait=1`：

```text
点击开始
→ HTTP 等到 Run terminal
→ 同时每 1.5 秒轮询 Room 展示进度
→ 请求完成后再刷新 Room
```

这是迁移期折中：

- 优点：沿用旧调用方的“请求完成即有完整结果”语义；
- 缺点：长 HTTP 请求仍可能受代理超时影响，typed client 的 `202` 和事件能力没有被主页面使用。

后续切换纯异步前端不需要重做 Store 或 RoundRun，只需要：

1. 主按钮调用 `runR2/runR3`；
2. 立即应用返回的 Room / run_id；
3. 用事件游标或轮询跟踪 Run；
4. terminal 后停止跟踪。

## 12. 已知边界为什么重要

### 一个房间当前只有一个 R2 和一个 R3

`UNIQUE(room_id, round)` 很好地解决首次讨论的重复启动，但它没有“讨论周期”维度。

BriefVersion 已允许 R2 后产生新版本并回到 R1，然而同一房间再次启动 R2 时，Store 会找到第一次的 R2 Run。当前
不能在原房间完成第二个 R1 → R2 → R3 周期。

这不是单纯放宽唯一键就能解决。正确扩展需要：

- `cycle_id` 或用确认 Brief version 作为 Run 维度；
- Turn 归属到 cycle / run；
- Summary 按 cycle 保存；
- 事件和前端历史区分多个周期；
- 明确旧 ACP 会话是复用还是重建。

在这套模型落地前，重新讨论应创建新房间。

### `failed` 不是普通前进状态

基础 Room 状态机把 `failed` 视为终态，避免任意代码把失败房间重新推进。只有明确的恢复事务可以：

```text
failed/summary → summarizing_r2 或 summarizing_r3
```

这是受控例外，不应新增通用 `failed → 任意状态` 转换。

### `canceled` 目前只是预留

类型和终态判断认识 `canceled`，但当前没有取消 API、取消执行信号或前端按钮。文档和 UI 不应承诺用户可以中止正在
运行的席位。

## 13. 不变量

当前实现依赖以下不变量：

1. 一个房间固定一个裁判和五个职能席。
2. R2/R3 进度总数固定为五，不包含裁判。
3. Agent 只能 propose Brief，只有用户能确认。
4. R2 和 R3 使用同一个 `r2_brief_version` 快照。
5. R2 首轮席位互不可见。
6. R3 必须 resume 本席 ACP 会话并读取 R2 公开上下文。
7. 同一 Run 的正常席位执行门最多打开一次。
8. Summary₂ 未通过工具提交与 runner 核验时，R3 不可启动。
9. Summary₃ 未通过工具提交与 runner 核验时，Room 不可 Done。
10. 席位失败恢复不能重跑已经完成的席位。
11. Run terminal 状态与 Room 阶段在同一事务中 finalize。
12. 主时间线默认只绑定 `content_text`；tool / thinking 保留在 process。

破坏其中任何一条，都需要同时更新 Store 事务、状态投影、恢复动作和自动化测试。
